# ATM System

Система банкомата на .NET 10 с REST API и консольным клиентом. Администратор создаёт счета, а пользователь входит по номеру карты и PIN-коду, проверяет баланс, пополняет счёт и снимает деньги. Сервер хранит данные в PostgreSQL и записывает историю операций.

Клиент и сервер запускаются как отдельные приложения и общаются по HTTP. Такое разделение позволяет менять консольный интерфейс независимо от правил работы со счётом и использовать API с другими клиентами.

## Возможности

- Администратор входит по системному паролю и может создать несколько счетов за один запрос.
- Пользователь входит по номеру карты и PIN-коду. После входа сервер выдаёт идентификатор сессии `Guid`, который клиент передаёт в следующих запросах. Повторно вводить реквизиты для каждой операции не нужно.
- Сервер проверяет роль сессии: создание счетов доступно администратору, операции со своим счётом доступны пользователю. Счёт определяется по пользовательской сессии.
- При снятии система проверяет сумму и остаток на счёте. Пополнение отклоняет отрицательную сумму.
- В историю попадают пополнения, снятия и проверки баланса. Для каждой записи сохраняются время и данные операции, чтобы пользователь мог просмотреть действия со счётом.

## Архитектура

Сервер построен по принципам луковой архитектуры. Доменная модель находится в центре, прикладные сервисы выполняют сценарии, а работа с PostgreSQL и HTTP вынесена во внешние слои. Направление зависимостей закреплено ссылками между проектами: модель счёта не зависит от Npgsql или ASP.NET Core.

### Доменная модель

`Account` содержит методы `TryDeposit` и `TryWithdraw` и сам проверяет допустимость изменения баланса. Например, попытка снять больше доступного остатка возвращает отказ и сохраняет прежний баланс. Благодаря этому правила находятся в одном месте, а HTTP-контроллеры и консольные команды не дублируют проверки.

Для денежных значений используется `Money` на основе `decimal`. Этот тип запрещает отрицательное значение при создании. Идентификаторы счетов, операций и сессий представлены отдельными типами `AccountId`, `OperationId` и `SessionId`. Они помогают различать значения по назначению при передаче между методами.

### Прикладные сервисы и контракты

`AccountService` связывает проверку сессии, работу со счётом и запись истории. `SessionService` проверяет данные для входа и создаёт сессии. Контроллеры принимают HTTP-запросы, вызывают эти сервисы и переводят результат в HTTP-ответ. Такое разделение позволяет проверять сценарии без запуска веб-сервера.

В `Contracts` находятся запросы, DTO и варианты результатов операций. Например, снятие возвращает `Success`, `NotUserSession` или `Failure`. Ожидаемые отказы передаются как данные, поэтому контроллер явно выбирает ответ, а клиент получает сообщение об ошибке. DTO отделяют формат обмена данными от доменных объектов.

### Интерфейсы хранилища и внедрение зависимостей

Прикладные сервисы обращаются к `IAccountRepository`, `ISessionRepository` и `IOperationRepository` через `IPersistenceContext`. Реализации репозиториев находятся в инфраструктурном слое. Это позволяет подменять хранилище в тестах, сохраняя код банковских сценариев.

Microsoft Dependency Injection связывает интерфейсы с реализациями в точках запуска приложений. Регистрация каждого слоя вынесена в методы расширения, поэтому состав приложения можно увидеть в `Program.cs`, а сервисам не приходится самостоятельно создавать свои зависимости.

## Работа с базой данных

### PostgreSQL и Npgsql

В PostgreSQL хранятся счета, сессии и история операций. Репозитории выполняют SQL через Npgsql. Запросы написаны явно: в коде видно, какие поля читаются, как фильтруются записи и что обновляется.

Значения передаются через параметры SQL. Для записи коллекций счетов и операций используется `unnest`, поэтому несколько записей можно отправить одним запросом вместо отдельного обращения к базе для каждой из них.

### Транзакции

При пополнении и снятии запись операции и обновление баланса выполняются в рамках `IPersistenceTransaction`. Его реализация использует `TransactionScope` с поддержкой асинхронных вызовов. Подтверждение происходит после обеих записей; при выходе без подтверждения транзакция откатывается. Это связывает изменение счёта с соответствующей записью в истории.

### Миграции

FluentMigrator управляет созданием таблиц через версионируемые миграции с SQL в методах `Up` и `Down`. При запуске API применяет недостающие миграции. Благодаря этому структуру базы можно получить из репозитория без ручного создания таблиц, а изменения схемы хранятся рядом с кодом.

### История операций

Общие поля операции хранятся в столбцах таблицы, а данные конкретного типа записываются в `jsonb`. У пополнения и снятия это сумма, у проверки баланса это остаток. Такой формат позволяет хранить разные операции в одной таблице без отдельных столбцов для каждого варианта.

Преобразование операций между доменной моделью и моделью хранения организовано как цепочка обработчиков. Каждый обработчик отвечает за свой тип. Логика преобразования отделена от SQL-кода репозитория.

Репозиторий читает историю от новых записей к старым, используя `LIMIT` и курсор по `operation_id`. Запрос выбирает страницу записей, поэтому для просмотра части истории не требуется загружать её целиком.

## Консольный клиент

Spectre.Console отвечает за формы ввода, скрытый ввод PIN-кода и пароля, сообщения и таблицу истории. Spectre.Console.Cli разбирает команды и вызывает соответствующие обработчики. Это позволило собрать интерактивный интерфейс с проверкой ввода и отдельной командой для каждого действия.

`ClientContext` хранит идентификатор текущей сессии в памяти процесса. Обработчики команд передают его автоматически, поэтому пользователь работает с командами без ручного копирования `Guid`.

HTTP-вызовы описаны интерфейсами Refit. Библиотека формирует запросы и преобразует JSON в модели ответа. Обёртки `AccountClient` и `SessionClient` проверяют ответы `IApiResponse<T>` и возвращают результаты прикладному слою. Благодаря этому обработчики консольных команд работают с результатами банковских операций и не собирают HTTP-запросы вручную.

## Настройки и документация API

Параметры подключения к PostgreSQL и системный пароль задаются в конфигурации сервера. Клиент читает адрес API и настройки интерфейса через User Secrets. Настройки связаны с типизированными классами через Options и проверяются с помощью Data Annotations. Это позволяет менять параметры подключения без правки сервисов и обнаруживать некорректные значения при получении настроек.

API публикует описание OpenAPI и интерфейс Scalar. Через него можно посмотреть модели запросов и ответов и вызвать методы сервера при проверке API.

## Тестирование

В `tests/Service.Application.Tests` используются xUnit и NSubstitute. Репозитории и провайдер транзакций заменены тестовыми реализациями, поэтому тесты проверяют прикладной сервис без PostgreSQL.

Проверяются четыре сценария: снятие при достаточном остатке, отказ при нехватке средств, пополнение допустимой суммой и отказ при отрицательной сумме. В каждом случае проверяются результат операции и баланс. Эти проверки помогают заметить изменения, которые нарушают правила пополнения и снятия.

## Структура решения

| Путь | Назначение |
| --- | --- |
| `src/service/ATMService/` | Запуск API, конфигурация и подключение слоёв сервера. |
| `src/service/Service.Application/` | Доменная модель, прикладные сервисы, контракты и интерфейсы хранилища. |
| `src/service/Service.Infrastructure/` | Репозитории PostgreSQL, миграции и реализация транзакций. |
| `src/service/Service.Presentation/` | HTTP-контроллеры и модели запросов и ответов. |
| `src/console-client/ConsoleClient/` | Запуск клиента, регистрация зависимостей и цикл чтения команд. |
| `src/console-client/ConsoleClient.Application/` | Клиентские сценарии, модели, контракты и интерфейсы HTTP-клиентов. |
| `src/console-client/ConsoleClient.Infrastructure/` | Реализации обращений к API через Refit. |
| `src/console-client/ConsoleClient.Presentation/` | Обработчики команд, ввод данных и вывод результатов. |
| `tests/Service.Application.Tests/` | Тесты пополнения и снятия средств. |
| `docker/` | Конфигурация PostgreSQL для локального запуска. |
| `labs/` | Условия лабораторных работ. |

Версии пакетов собраны в `Directory.Packages.props`, а общие параметры сборки и анализаторов заданы в `Directory.Build.props`. Это позволяет поддерживать одинаковые версии зависимостей и правила проверки кода во всех проектах решения.
